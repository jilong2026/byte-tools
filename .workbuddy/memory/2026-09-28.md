## 排查：CI 同步产物到 Gitee Release 失败（v1.0.2）

- 失败点：`.github/workflows/release.yml` 的 `sync-to-gitee` job，step「创建 Gitee Release」（日志 `[1/2]`）。
- 报错：`curl: (35) OpenSSL SSL_connect: SSL_ERROR_SYSCALL in connection to gitee.com:443`，exit 35。
- 结论：curl 35 是 TLS 握手阶段底层 TCP 被重置/超时，HTTP 请求未发出，与 token、owner/repo、参数无关（那些会返回 401/404 JSON）。
- 验证：本机（国内网络）curl `https://gitee.com/api/v5/repos/jack_liujilong/byte-tools` 返回 200 / 0.3s，Gitee 服务与仓库路径均正常 → 根因是 GitHub Actions runner（境外）到 gitee.com 的国际链路不稳定。
- 附带发现：step 顺序是「先发布 GitHub Release，再同步 Gitee」，所以 Gitee 失败时 GitHub 侧产物已完整，只需 rerun 失败 job 或手动补传。
- 历史相关：v1.0.3 / v1.0.4 的 Gitee 同步失败是另一个坑——macos-13(Intel) runner 下线导致 job 永久 queued（已在 workflow 注释中停用该 matrix 项）。
- 建议方向（尚未实施，待用户确认）：Gitee 相关 curl 加 `--retry/--retry-all-errors/--connect-timeout`；或把 sync-to-gitee 放到国内 self-hosted runner / 改本地脚本。

### 写 Windows 批处理踩到的四个坑（重要，可复用）

1. **UTF-8 编码的 .bat 会被 cmd 按 GBK 解析，中文乱码会破坏语法**（表现为 `'xxx' is not recognized`、行被莫名截断）。要么文件存 GBK（GitHub 上显示会乱码），要么内容保持纯 ASCII。本项目选后者：文件名中文、内容全英文。
2. **`for /f "usebackq" ... in (`命令`)` 内嵌命令不能含单引号**——usebackq 下单引号被当作字面字符串，解析直接崩。改为「PowerShell 写临时文件（ASCII）+ bat 用 `set /p` / `findstr` 读取」。
3. **PowerShell 5.1 不支持 `if` 表达式赋值**（`$x = if (...) {...}` 是 PS7 语法），也不允许 `catch {} | Out-File` 这种把管道接在语句块后。要在块内输出。
4. 从 Git Bash 传中文文件名给 `cmd //c` 会因编码损坏找不到文件；测试时复制成英文临时名再跑。PowerShell 工具则禁止调用 cmd.exe。
